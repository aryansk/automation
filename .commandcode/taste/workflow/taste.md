# Taste

## Verification & handoff
- When resuming an interrupted task, do not restart the implementation or rebuild completed deliverables — verify what exists and finish from there; do not rerender/regenerate expensive outputs (videos, atlases) unless an output is missing, corrupt, or inconsistent with the final source. Confidence: 0.95
- Before launching any render or build command, always check whether the output file already exists on disk first — never assume it needs to be (re-)run without checking. If the render is already done, skip rebuilding and just confirm the file. When the user indicates the work is already done, believe them and verify immediately rather than continuing to poll a background task. Confidence: 0.95
- Make only necessary fixes and preserve the existing visual system and API — no broad rewrites on continuation tasks; never delete or overwrite existing completed renders, snapshots, or unrelated user work. Confidence: 0.85
- Never claim a check passed unless it was actually run or directly verified — report only what was really executed, and verify the actual output rather than assuming. Confidence: 0.95
- When full-suite tests fail, clearly distinguish failures caused by the new work from unrelated pre-existing repository failures (e.g., stale tests referencing deleted legacy files). Confidence: 0.9
- Wants final handoffs to be concise and list: completed deliverables, rendered example paths, validation evidence, any remaining unrelated repository issues, and the exact files changed. Confidence: 0.9
- Before committing, wants a structured pre-commit audit: a focused `git status` limited to the work's own files, `git diff --stat`, full focused diff review for accidental/unrelated changes, deletion-safety verification (no dangling imports, scripts, doc links, runtime paths, or tests), confirmation that no existing production story/composition/render/narration file was overwritten, an explicit statement of which generated artifacts would be committed, and a final run of tests + validators + syntax checks. Confidence: 0.85
- Wants the pre-commit audit to end in an explicit binary verdict ("SAFE TO COMMIT" / "NOT SAFE TO COMMIT"); when unsafe, list only concrete blockers and fix none until instructed — and make no implementation changes during an audit unless a concrete defect is found. Confidence: 0.9
- In commit tasks, if staging reveals a concrete broken import or missing required file (e.g., a staged file imports an untracked/unstaged core library absent from the manifest), stop without committing and report the blocker rather than silently expanding the manifest or making unilateral git decisions; leave the tree clean (unstage) and untouched. Confidence: 0.9
- Cares about git hygiene for generated artifacts: renders/MP4s and QA inspection frames should remain local or be explicitly flagged as would-be-committed; prefers an explicit commit file-list over a blanket `git add -A` that could sweep in unrelated untracked directories and pre-existing uncommitted work. Confidence: 0.85
- Include exact copy-pasteable commands (e.g., macOS `open` paths to the rendered MP4s) so the user can verify deliverables themselves. Confidence: 0.7
- For large visual/rendering revisions: validate short representative samples first (each key preset family, both aspect ratios, with frame inspection) before committing to expensive full-length renders; write new renders to distinct filenames and keep the previous renders untouched until the revised system is verified. Confidence: 0.85
- Visible UI and documentation should describe the system accurately (e.g., "globe animation library" rather than "globe/map library") even when internal filenames and API fields keep legacy names for compatibility. Confidence: 0.65

- When a foreground render exceeds the timeout, re-run it as a background process (`run_in_background: true`) with no timeout rather than trying to optimize the render to fit the foreground window; monitor progress periodically via the background task output. Confidence: 0.8
- For long background renders, redirect output to a `/tmp` log file and poll progress via the log and the output file on disk — npm/pipe buffering can make `tail` of task output appear empty until the process actually completes. Confidence: 0.75
- The render file is the source of truth over the history ledger: if a story is recorded in `story-history.json` but its MP4 deliverable is missing, re-render it to the canonical path with `--allow-history` (the no-repeat gate is bypassed only for legitimate re-renders of missing outputs). Confidence: 0.75
- During visual QA of a multi-story render, sample frames from every story segment (not just the opener or first story) and transcribe the on-screen text to verify each card renders — one story looking right doesn't prove the rest. Confidence: 0.7
- When a defect is reported (e.g., "the last videos didnt have the openshot titles ... make sure that never happens again"), the user expects a permanent, verified fix: root-cause it, confirm the fix in actual rendered frames (extract frames and verify the element appears), and re-render every deliverable produced before the fix — a fix counts only when all outputs demonstrably contain the element, not when the code merely looks correct. Confidence: 0.85
- When a bug is found in the shared video template/renderer, the user expects the fix to be applied at the root cause and propagated to every project copy (not just the one episode being fixed) so the defect "never happens again" — e.g., a globe-layer bug found in one explainer had to be synced to all landscape project renderers, not patched in isolation. Confidence: 0.85
- When the user says they fixed a defect themselves ("i fixed them", "i have fixed the first two"), treat their fix as the new source of truth: confirm it is in place in the code, identify which earlier renders predate it, and re-render those stale outputs — do not undo, redo, or compete with the user's fix. Confidence: 0.85
