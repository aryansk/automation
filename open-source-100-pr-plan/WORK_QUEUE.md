## Queue update rules




- One thread may have one primary `IN PROGRESS` item unless a dependency is
  purely administrative.
- `WAITING` means the item is ready in principle but depends on an earlier
  queue item; it is not blocked by an external failure.
- `BLOCKED` must include the concrete blocker and the condition that would
  unblock it.
- When work finishes, add evidence and a work-log entry before changing the
  status to `DONE`.
- When priorities change, record why in `WORK_LOG.md`; do not silently reorder
  the queue.
- For `OPS-026` and later packets, `RESERVE` is only a lightweight lead. Do
  not implement or claim a reserve item until it passes a fresh live
  preflight. Process one lane through `PUBLISHED` or an explicit stale/blocked
  exit before selecting the next lane; the state file records the four lane
  timestamps and prevents more than one active lane.
- Run the live preflight twice for every lane: once immediately before
  implementation and once immediately before push/publication. Recheck issue
  open/assignment/claim state, overlapping or recent unlinked PRs, repository
  policy and identity gates, base branch, scope, and validation path. If any
  check fails, record the reason and move to the next reserve candidate without
  sunk-cost justification.
- Count a lane only after canonical URL, author, intended base, matching head
  hash, open/draft state, and explicit verification are recorded as
  `PUBLISHED`. A closed or duplicate publication is invalidated and replaced
  while the run is active when a reserve lane is available.
- After the complete five-PR packet is verified, create or update one
  deduplicated Notion row per submitted PR and recompute the Submitted-per-day
  chart once before closing the task. If the batch dashboard sync fails, record
  the blocker and leave the publication task visibly incomplete.
- Whenever a canonical PR is verified merged, update its existing tracker row
  with the GitHub `merged_at` date, merge commit, `PR Status = Merged`, and
  `Counted = true`, then create or update one `PRs Merged` row per merge date
  in `📈 Unified Daily Activity`. Use one aggregated row per date and never
  treat the check date as the merge date.
